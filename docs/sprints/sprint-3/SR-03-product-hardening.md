# SR-03 — Product hardening

| | |
|---|---|
| **Linked requirements** | NFR-11 (performance), NFR-12 (responsive UI), NFR-13 (accessibility basics), NFR-05 (no double booking, optional database guard) |
| **Proposed carry-over** | NFR-14 (login throttling), NFR-10 (release SHA in `/api/health`), see §2.4 |
| **Depends on** | All feature work: F-01 to F-14 |
| **Sprint** | 3 |
| **Contract version** | 0.1 (draft, 2026-11-28). See [version history](#version-history). |

SR-03 is a supporting requirement, not a user feature. It adds no screen. It proves, with scripts that anyone can run,
that the finished product is fast enough, usable on a phone and usable without a mouse. Each item below has a
command that passes or fails.

## 1. Behavior and workflow

1. **Performance.** A script seeds a **separate** database with 500 items and 5,000 requests, logs in through the real
   API, calls each endpoint 50 times one after another, and prints the median, the 95th percentile and the slowest
   time. It exits with an error when the 95th percentile of a required endpoint is 500 ms or more.
2. **Responsive.** A Playwright run opens every screen in §2.2 in a 360 × 640 phone window and checks that the page
   does not scroll sideways.
3. **Accessibility.** The same run scans every screen with axe-core and fails on any *serious* or *critical*
   violation, once in the light theme and once in the dark theme. A second run drives three journeys with the keyboard
   only.
4. **Optional database guard.** A migration adds a PostgreSQL exclusion constraint so that two overlapping
   `APPROVED` or `CHECKED_OUT` bookings of one item cannot exist even if the application has a bug (see §2.3).

## 2. Rules and measurements

### 2.1 Performance (NFR-11)

| Item | Rule |
|---|---|
| Data | 500 items (spread over the categories, a few `MAINTENANCE`, a few `RETIRED`), 5,000 requests (all six statuses, dates spread over a year, some overdue loans), 100 Borrowers and one Custodian. Generated by `server/scripts/perf-seed.ts` with a fixed random seed, into the database `inventory_perf`. It never touches the development or test database, and it refuses to run against a `DATABASE_URL` whose name does not end in `_perf`. |
| Run | `bun run perf` in `server/`. Starts the app on a random port, logs in as a Custodian, runs 5 warm-up calls (not counted), then 50 sequential calls per endpoint. |
| Required (NFR-11) | `GET /api/items` and `GET /api/requests`: p95 **< 500 ms** |
| Also measured and reported against the same 500 ms target | `GET /api/items?q=uno&freeFrom=…&freeTo=…` (F-11), `GET /api/items/:id/history` for the item with the most loans (F-12), `GET /api/dashboard` (F-13), `GET /api/reports/requests.csv` for a 366-day range (F-14) |
| Output | A table with the endpoint, median, p95 and maximum in ms, the machine description and the commit. It is saved as evidence. |
| If a required endpoint is too slow | Fix it before release. The planned fixes are an index (`pg_trgm` for `q`), a narrower `select`, or a `limit`. Each fix is a PR with its own test. |

### 2.2 Screens for NFR-12 and NFR-13

| Role | Screens |
|---|---|
| Anonymous | `/login` |
| Borrower | `/items`, `/items/:id`, `/my-requests` |
| Custodian | `/requests` (the four tabs), `/overdue`, `/items`, `/items/:id` (with the history), `/manage/items`, `/manage/items/new`, `/manage/items/:id`, `/manage/categories`, `/dashboard`, `/reports` |

Each screen is opened with data on it (the E2E fixture), not empty, so a long name or a table can overflow.

**NFR-12 check:** at 360 × 640, `document.documentElement.scrollWidth` is at most `window.innerWidth`, and every
button, link and field that a user can press is at least 44 px high.
**NFR-13 check:** axe-core, rule sets `wcag2a`, `wcag2aa`, `wcag21a` and `wcag21aa`, reports no violation with impact
`serious` or `critical`. Violations with impact `minor` or `moderate` are listed in the evidence and either fixed or
recorded as known limitations.
**Keyboard check:** with only Tab, Shift+Tab, Enter, Space and Esc: (1) log in; (2) a Borrower opens an item, fills the
request form and submits it; (3) a Custodian opens the reject dialog, types a reason, closes it with Esc, and approves
a request. A failed focus (a control that cannot be reached, or a dialog that does not return focus) fails the run.

### 2.3 Optional: exclusion constraint (NFR-05)

| Item | Rule |
|---|---|
| Migration | `CREATE EXTENSION IF NOT EXISTS btree_gist;` then `ALTER TABLE "BorrowRequest" ADD CONSTRAINT "BorrowRequest_no_double_booking" EXCLUDE USING gist ("itemId" WITH =, daterange("startDate", "dueDate", '[]') WITH &&) WHERE ("status" IN ('APPROVED', 'CHECKED_OUT'));` Additive. Rollback: drop the constraint. |
| What it does not cover | The overdue extension of BR-03 (F-08) depends on today's date, so it cannot be a constraint. The application rule stays the main rule. The constraint guards the stored periods. |
| Go / no-go | Before the migration runs on any shared database, this query must return 0 rows: the same overlap test over existing `APPROVED` and `CHECKED_OUT` rows. If it returns rows, the migration is **not** applied and the finding is recorded as a defect. The extension must be allowed on Cloud SQL (it is a trusted extension in PostgreSQL 13 and later). If either check fails, this item is dropped and recorded as not done. NFR-05 stays covered by the row lock (TEST-34). |
| App behavior | A constraint violation (`23P01`) maps to the same 409 `PERIOD_UNAVAILABLE` as the application check. |

### 2.4 Proposed carry-over from SR-02 (needs an approved scope revision)

[plan.md D3](../plan.md) puts these two in SR-02 (Sprint 2). They are **not implemented** at the date of this contract.
The Deliverable 2 sheet says a required Sprint 2 item cannot be moved to Sprint 3 just to close Sprint 2. So they are
written here as proposed, and they count as Sprint 3 work only after the scope revision is approved and recorded in
[traceability.md §B3](../../traceability.md#b3-approved-changes). Until then they are open Sprint 2 gaps. Note that
change CH-01 already moved NFR-14 **from** SR-03 **to** SR-02 (the service is public from Sprint 2), so moving it back
needs a new change record that gives the reason and the date.

- **NFR-14, login throttling.** After 5 failed logins for the same email within 15 minutes, further logins for that
  email get 429 `TOO_MANY_ATTEMPTS` ("Too many attempts. Try again later.") until the window passes, **even with the
  correct password**. Other emails are unaffected. The failures are stored in a new table
  `LoginFailure (id, email, failedAt)` with an index on `(email, failedAt)`, added by an additive migration, so the
  count survives a restart and a redeploy (NFR-07). The email is lower-cased as at login. An unknown email counts too,
  so the response does not reveal which emails exist. A successful login does not clear the failures.
- **NFR-10, release SHA.** `GET /api/health` returns `{ "status": "ok", "commit": "<40 hex>" }`. The value comes from the
  environment variable `GIT_COMMIT`, which the image build sets (`ARG GIT_COMMIT` and `ENV GIT_COMMIT` in the
  Dockerfile, passed by `deploy.yml` from the commit being built). Without it, `commit` is `"unknown"`. The smoke
  test then checks that the running commit equals the deployed image tag.

## 3. Permissions

No change. The endpoints measured keep their F-xx permissions. The performance script uses a Custodian token, which is
the broadest role. `GET /api/health` stays public (§2.4).

## 4. API

No new endpoint. §2.4 changes one response (`/api/health` gains `commit`) and one error (login can return 429).

## 7. Acceptance criteria

| AC | Given / When / Then |
|---|---|
| **AC-114** | **Given** the performance data of §2.1, **when** `bun run perf` runs, **then** `GET /api/items` and `GET /api/requests` each have a p95 below 500 ms over 50 sequential calls, and the command exits with 0. The other endpoints in §2.1 are reported. A p95 of 500 ms or more for a required endpoint makes it exit with an error. |
| **AC-115** | **Given** the screens in §2.2 with data, **when** each is opened at 360 × 640, **then** there is no horizontal scroll and every control a user can press is at least 44 px high. |
| **AC-116** | **When** axe-core scans each screen in §2.2 in the light and in the dark theme, **then** there is no violation with impact `serious` or `critical`. |
| **AC-117** | **When** the three journeys of §2.2 are driven with the keyboard only, **then** each completes, focus is visible at each step, and **Esc** closes the reject dialog and returns focus to the **Reject** button. |
| **AC-118** | **Optional.** **Given** the migration of §2.3, **when** two overlapping `APPROVED` rows for one item are inserted directly with SQL, **then** the database refuses the second one. Two concurrent approvals through the API still give one 200 and one 409. Non-overlapping and touching-but-separate periods, `PENDING` rows and other items are unaffected. |
| **AC-119** | **Proposed (§2.4).** **Given** 5 failed logins for `borrower1@example.test` within 15 minutes, **when** the 6th login is sent with the correct password, **then** 429 `TOO_MANY_ATTEMPTS` and no session is created. Another email still logs in. After 15 minutes (the injected clock) the correct password works. 4 failures followed by the correct password still logs in. |
| **AC-120** | **Proposed (§2.4).** **When** the image is built with `GIT_COMMIT=<sha>`, **then** `GET /api/health` returns that `commit`. Without it, `commit` is `"unknown"`. The post-deploy smoke test fails if the reported commit differs from the deployed tag. |

Tests: see [sts.md](sts.md) (TEST-135 to TEST-141).

## 8. Definition of Done

1. Every AC above that is in scope is implemented and shown by a command with its output. The optional and the proposed
   items are either done and shown, or recorded as not done with the reason.
2. The performance, responsive, accessibility and keyboard checks ran on the release commit. Their output is kept as
   evidence, with the pass, fail and skip counts, and no check was weakened to pass.
3. Every violation that is not fixed is listed with its impact, the screen and the reason.
4. The scripts are in the repository and documented in the README (command, data, expected output).
5. The PRs were reviewed by the other student and CI is green. The contract, STS and traceability match the code.
